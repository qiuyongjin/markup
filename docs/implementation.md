# 技术实现

本文记录 mdoc 编辑器的实现思路：Markdown 怎么解析、编辑时 DOM 和源码怎么同步、光标怎么定位，以及测试方案。

## 整体结构

```text
src/
├── core/                 # 零依赖层：端口类型与日志端口
│   ├── types.ts          # LinkCandidate / LinkProvider / OpResult / SuggestResult
│   └── logger.ts         # 可注入的 logger，默认 no-op
├── markdown/             # Markdown 语法（与框架无关）
│   ├── parser.ts         # 源码 -> token 树
│   └── dom.ts            # token 树 <-> DOM 互转，光标位置在源码与 DOM 之间映射
├── editor/               # 编辑器层：编排 core + markdown
│   ├── editor.ts         # 编辑器核心：拦截按键、修改源码、重新渲染、还原光标
│   ├── types.ts          # 编辑器对外的契约（EditorOptions / SuggestionState）
│   ├── text.ts           # 字素簇与单词边界（纯函数）
│   └── history.ts        # 撤销 / 重做栈（纯数据）
├── pages/
│   └── store.ts          # 页面仓库：候选窗口的来源，页面只存在内存里
└── components/
    ├── MarkdownEditor.vue   # 挂载编辑器 + 渲染候选窗口
    ├── LinkSuggest.vue      # 候选窗口本身
    ├── PagePopup.vue        # 页面弹窗
    └── DevStats.vue         # dev-only 的性能 HUD
```

依赖方向是单向的：

```text
components/  ──►  editor/  ──►  markdown/
     │             │
     │             └──►  core/      （端口类型、日志端口）
     │
     └──►  pages/  ──►  core/
```

- `core/` 是零依赖层：不 import vue，不碰 `document` / `window`；
- `editor/` 不知道页面存在，只通过 `LinkProvider` 端口取数据；
- `pages/` 不 import `editor/`（页面领域的端口类型在 `core/types.ts`）；
- 组件层不 import `pages/`：页面仓库的具体实现只在组合根出现，
  组件只通过 `links` 属性拿到 `LinkProvider` 端口；
- 组合根（`App.vue`）是唯一把页面仓库注入编辑器的地方。

这几条规则由 `test/architecture.test.ts` 守着，改坏了测试会红。

`editor/editor.ts` 不依赖任何框架，`MarkdownEditor.vue` 只负责把它挂到
`contenteditable` 元素上。页面仓库（`store.ts`）用了 Vue 的响应式，
编辑器只通过一个接口（`LinkProvider`）跟它打交道。

### 端口与失败

`LinkProvider` 的方法都返回**结果**而不是 `void`：

- `suggest()` 返回 `{ candidates, error? }`：`error` 有值说明是「查询挂了」，
  和「没有匹配页面」在界面上必须能区分开；
- `create()` 返回 `{ ok: true }` 或 `{ ok: false, error }`：建页失败不再静默。

### 可观察性

- `core/logger.ts` 定义可注入的 `Logger`，默认 `noopLogger`（生产环境什么都不记）；
- 开发环境由 `MarkdownEditor.vue` 注入 `consoleLogger()`；
- 编辑器每次渲染后记一条 debug 日志（源码长度、元素数、解析与渲染耗时）；
  两处原本「静默吞异常」的空 `catch`（光标定位、选区定位）现在会留下 warn 日志
  —— 保留「忽略这个异常」的语义，但不丢弃信息；
- dev 下挂载性能 HUD（`DevStats.vue`），显示源码长度 / 元素数 / 解析耗时 / 渲染耗时。
  它用 `import.meta.env.DEV` 守卫 + 动态 import，生产构建里不进包。

## 解析器

### 支持的语法

目前实现四种语法，且不依赖任何第三方 Markdown 库：

| 语法 | 写法 | 规则 |
| --- | --- | --- |
| 标题 | `# 文字` | 必须是行首的 1~6 个 `#`，后面跟至少一个空格；空格算标记的一部分，会被吃掉 |
| 加粗 | `**文字**` | 标记必须成对出现，依次配对（第 1 个配第 2 个，第 3 个配第 4 个） |
| 行内代码 | `` `文字` `` | 同上，且优先级高于加粗，代码内部不再解析其它语法 |
| 双向链接 | `[[页面名]]` | 页面名是纯文本（不能含方括号、反引号、换行），链接内部不再解析其它语法 |

没有配对的标记会被当作普通文字原样显示。

标题的空格没打出来之前（`#`、`#标题`）也按普通文字处理，
这样 `#今日分享` 这样的标签不会被误判成标题；
`####### 标题`（七个井号）同理。

### 解析流程

1. **按行拆块**：逐行判断是不是标题（行首 1~6 个 `#` 加空格）。
   标题行单独成块，标题正文里的行内语法单独解析（标题和后面的内容互不影响）；
   其余的行合并成段落——这样跨行的加粗、行内代码依然能配对，
   和文档里没有标题时的表现一致。
2. **找代码区间**：在每一块里从左到右扫反引号，第 1 个与第 2 个配对，第 3 个与第 4 个配对，落单的反引号不处理。
3. **找链接区间**：跳过代码区间，继续扫 `[[`，找配对的 `]]`。
   页面名里出现方括号、反引号或换行就不算链接；和代码区间重叠的候选也放弃（代码优先）。
4. **找加粗区间**：跳过代码区间和链接区间，继续扫 `**`，同样依次配对。配对结果是「内容区间」，
   例如 `**abc**` 得到内容区间 `[2, 5)`。
5. **组装 token 树**：把代码区间、链接区间和加粗区间转成一串事件（`code` / `link` / `boldOpen` / `boldClose`），
   按位置排序后线性扫描，用一个栈维护嵌套关系，产出 token 树。

事件上除了位置还带两个字段，用来保证标记本身既不出现在内容里、也不会漏掉：

- `textEnd`：本事件之前的普通文本到哪里结束（跳过起始标记）
- `resume`：本事件处理完之后，普通文本从哪里继续（跳过结束标记）

```ts
type Token =
  | { kind: 'text'; text: string }
  | { kind: 'bold'; children: Token[] }
  | { kind: 'code'; text: string }
  | { kind: 'link'; name: string }
  | { kind: 'heading'; level: number; marker: string; children: Token[] }
```

### 词法分析是线性的

扫描区间时，「当前位置在不在某个区间里」这类查询用**游标**（`SpanCursor`）完成：
区间按 `start` 升序且互不重叠，查询的偏移又是单调递增的，
所以游标只向前推进就行，整体复杂度是「字符数 + 标记数」。

早期版本用的是 `spans.find(...)`，每次都从数组头扫一遍，
复杂度变成「字符数 × 标记数」——**长篇没有标题的散文**会撞上这个悬崖
（50KB 一次解析要 90ms，100KB 要 400ms）。
带标题的笔记不会触发：标题是块的天然切分点，一篇文档被切成很多小块，
每块都很短。详见 `docs/architecture.md` 的 F5 与附录 B。

`pnpm test:perf` 是独立的性能回归脚本（不放进单元测试，避免 CI 机器抖动导致误报），
它只拦截「数量级退化」：最坏情况 52,000 字符必须 < 50ms，
字符数 ×4 时耗时不能超过 ×8。

## 编辑模型

### 为什么是「受控编辑」

最初的实现是让浏览器直接改 DOM，事后把 DOM 反序列化回 Markdown 源码。实测发现这样会丢内容：

- 行尾输入的空格会被 Chromium 换成 `&nbsp;`
- 在行内元素边界继续输入时，Chromium 会做空白规整，把加粗内容末尾的空格挪走甚至吃掉

也就是说，DOM 里看到的内容和用户真正输入的内容并不一致。

所以改成**受控编辑**：Markdown 源码是唯一数据源，DOM 只是它的渲染结果。

```text
按键 -> beforeinput 拦截 -> 修改 Markdown 源码 -> 重新渲染 DOM -> 还原光标
```

拦截的 `inputType`：

| inputType | 处理 |
| --- | --- |
| `insertText` | 在选区处插入文本 |
| `insertParagraph` / `insertLineBreak` | 插入换行 |
| `deleteContentBackward` / `deleteContentForward` | 删除一个字素簇 |
| `deleteWordBackward` / `deleteWordForward` | 删除一个单词 |
| `formatBold` | 给选区套上 `**` |
| `insertFromPaste` | 由 `paste` 事件处理，只取纯文本 |

这样源码永远和用户输入一致，浏览器的 DOM 改写行为不会再污染内容。

### 输入法组合输入

组合输入期间浏览器会直接改 DOM，此时不能拦截，所以：

- `compositionstart` 之后放行所有 `beforeinput`，让输入法正常工作
- `compositionend` 之后用 `serializeNodes()` 把 DOM 的变化收回成源码，再重新渲染

组合输入的位置有两个要注意的地方：

- 回车之后光标在末尾的占位元素里，候选文字会被插进这个元素（见「换行与最后一行」）
- 组合输入被取消时浏览器可能把占位元素换成 `<br>`，同步时要把它还原

退格按字素簇（grapheme cluster）删除，中文和 emoji 不会被拆开，用 `Intl.Segmenter` 实现。

## DOM 与源码的互转

### 渲染

标记元素上记录 `data-md` 属性，说明它对应哪个标记：

```html
<strong data-md="**">加粗</strong>
<code data-md="`">代码</code>
<h1 data-md="# " data-md-end="">标题</h1>
```

大多数标记是成对的，结束标记默认和起始标记一样。
标题没有结束标记（标题到行尾就结束了），所以用 `data-md-end=""` 显式说明。

### 反序列化

再走一遍 DOM，遇到带 `data-md` 的元素就用对应标记把内容包起来，于是 DOM 又变回源码。
没有 `data-md` 的元素（例如浏览器自己插入的 `<b>`）会走兜底规则。

兜底规则里有一条要特别注意：**`<em>` / `<i>` 会被还原成 `*…*`，而不是只留下文字**。
早先的写法是 `return serializeChildren(el, false)`，标记被静默丢掉了——
用户以为自己写的是斜体，回头一看标记没了，内容也变了。
现在按 Markdown 的习惯还原成 `*…*`：解析器还不认斜体，
至少标记还看得见，问题不会静默发生。

### 光标映射

源码里带标记，DOM 里没有，两者的位置对不上，所以需要在源码偏移量和 DOM 位置之间双向映射：

- `sourceOffsetAt(root, container, offset)` —— DOM 位置 → 源码偏移
- `positionForSourceOffset(root, target)` —— 源码偏移 → DOM 位置

映射的依据是每个节点的「源码长度」：文本节点是自身长度，带 `data-md` 的元素是
`起始标记长度 + 子节点长度 + 结束标记长度`（对加粗、行内代码来说，结束标记长度等于起始标记长度）。
两个方向的遍历用同一套长度计算，所以互为逆运算。

几个边界情况的处理：

- 源码偏移落在**起始标记**内部 → 光标落到内容开头
- 源码偏移落在**结束标记**内部 → 光标落到该元素之后
- 因此打完 `**` 让加粗闭合时，光标正好停在加粗内容**外面**，继续输入的文字不会跑进加粗里

### 标题为什么用行内块渲染

标题是块级语法，但 DOM 里它用的是 `display: inline-block`，原因有两个：

1. **不打断换行**：文档始终是一段连续的流，换行只靠文本节点里的 `\n`。
   标题如果用真正的块级元素（比如 `display: block`），标题后面那个 `\n`
   会把标题和正文之间多撑出一行空白；换行规则一变，
   光标在源码和 DOM 之间的映射就要为标题写特例。
2. **照样能有留白**：行内块支持 `margin`，所以标题上下一样有间距；
   长标题还会在自己的盒子里换行，不会和后面的正文混在一起。

空的标题（刚打完 `# `）保留标题的高度（`min-height`），
这样光标所在的那一行一眼就能看出是标题。

## 换行与最后一行

换行符直接留在文本节点里，靠 `white-space: pre-wrap` 显示成换行。但浏览器有个坑：

> 结尾的换行符不会生成行盒，最后一行没有高度。

后果是「输入 hello 后按回车没有换行」：源码里确实多了一个 `\n`，可屏幕上还是一行，
光标也被浏览器画在上一行的末尾（换行符的边界位置，浏览器一律画在上一行）。
按两次回车才会看到一行空白行——因为第二个 `\n` 让第一行有了行盒。

解决办法是给「以换行结尾的文档」补一个占位元素：

```html
hello\n<span data-md-tail></span>
```

它是一个极窄的行内块，撑出最后一行；光标也落在它里面（而不是换行符的边界上），
所以光标会真的停在最后一行。这个元素：

- 不代表任何源码：`sourceLength` 算它是 0，序列化时直接忽略
- 源码不再以换行结尾时就没有了（每次渲染都重新决定）
- 宽度至少 1px：零宽的盒子浏览器不会画光标
- 宽度要能跟着内容一起变宽（见下面的「输入法组合输入」）

对应到代码里就是三处：

| 位置 | 作用 |
| --- | --- |
| `editor.render()` | 源码以 `\n` 结尾时补上占位元素 |
| `positionForSourceOffset()` | 源码末尾的偏移映射到占位元素里，光标才会落在最后一行 |
| `styles/_editor.scss` | 占位元素的样式（至少 1px 宽、能变宽的行内块） |

### 输入法组合输入落在占位元素里

回车之后光标停在占位元素里，输入法的候选文字会被浏览器直接插进这个元素：

```html
hello\n<span data-md-tail>nihao</span>
```

如果占位元素的宽度写死成 1px，`white-space: pre-wrap` 下每个字母都会被折到单独一行，
用户看到的就是「一列一个字母」，直到选定候选词才恢复正常。所以占位元素用
`min-width: 1px` + `width: auto`：空的时候仍然只有 1px（光标照旧能画出来），
有内容时跟着内容一起变宽。

组合输入被取消（比如按 Esc）时，浏览器还会把占位元素换成一个 `<br>`。这个 `<br>`
只是浏览器给「空的最后一行」留的占位，并不代表源码里的换行，所以序列化时忽略
末尾的 `<br>`，同时每次同步都重新渲染一遍 DOM，把结构恢复成源码的样子。

## 双向链接

`[[页面名]]` 是指向「页面」的链接：页面名对应页面仓库（`src/pages/store.ts`）里的一条记录，
正文就是一段 Markdown 源码。页面之间可以互相链接，所以叫双向链接。

### 语法与渲染

链接在解析器里是一种行内标记，和加粗、行内代码走同一套流程：

- 优先级：行内代码 > 链接 > 加粗
- 页面名是纯文本，链接内部不再解析其它语法（`[[**a**]]` 的页面名就是 `**a**`）
- 没有配对的 `]]` 按普通文字处理，和其它标记一样

渲染出来是一个 `<a>` 元素，标记记在 `data-md` 上，序列化时能原样还原成源码：

```html
<a data-md="[[" data-md-end="]]" data-md-link="" data-page="hello">hello</a>
```

`data-page` 记着页面名，点击时用它找到对应的页面。

### 候选窗口

输入 `[[` 的时候，编辑器要弹出一个候选窗口。触发条件是「光标前面有一个还没闭合的 `[[`」：

1. 从光标往前找最近的 `[[`
2. 中间不能有 `]`（说明已经闭合了）、`[`（`[[[`）或换行（链接不跨行）
3. `[[` 到光标之间的内容就是查询词

候选列表由页面仓库给出（按查询词过滤，前缀命中的排前面），
再由编辑器组装成最终列表：

- 有同名页面：第一项就是那个页面
- 没有同名页面：第一项是「新建页面」，后面跟着匹配的已有页面
- 一个页面都没有：列表是空的，窗口里显示「输入内容并按回车，即可创建页面」

所以「输入 `[[hello` 按回车创建页面」和「输入 `[[` 从已有页面里挑一个」是同一个流程：
回车接受高亮的那一项，高亮的正是要用的页面名——不存在就先创建。

键盘：

| 按键 | 行为 |
| --- | --- |
| `↑` / `↓` | 切换高亮的候选项（到头会绕回来） |
| `Enter` / `Tab` | 接受高亮的候选项（一个候选都没有时不拦截，回车照常换行） |
| `Esc` | 关掉窗口；同一个 `[[` 不会再自动弹出来 |

窗口开着的时候默认高亮第一项，所以「回车选中的」永远就是「看到的那一项」。
编辑区失去焦点时窗口也会关掉。

窗口的位置跟着光标走（`getBoundingClientRect()`），
下面放不下的时候翻到光标上面，靠近屏幕边缘时也会收一收；
用上下键切换时，高亮的那一项会被滚回窗口里。

候选窗口的数据来源是注入的（`EditorOptions.links`），编辑器本身不知道页面怎么存：

```ts
interface LinkProvider {
  suggest(query: string): SuggestResult   // { candidates, error? }
  create(title: string): OpResult         // { ok: true } | { ok: false, error }
  exists?(title: string): boolean
  revision?: number                       // 页面数据变了就递增
}
```

`revision` 用来通知编辑器「该刷新断链的样子了」——
比「页面数量变了」可靠（增删改不一定改数量）。

### 断链

指向「还没有的页面」的链接会被标成断链（`a.is-missing`），
显示成灰色虚线，一眼能看出这个页面还没写。
页面创建之后（或者页面数据有变化时）重新标一下就行。

### 页面仓库

`src/pages/store.ts` 负责所有页面：查找、创建、更新、删除、按查询词搜索。
页面只存在内存里——刷新页面就没了，正文本来也是不存的。

仓库用工厂创建（`createPageStore()`），这样测试能拿到**隔离的实例**，
不会互相污染；模块级保留一个默认实例，现有 import 方式继续可用。
工厂的理由是**可测试**与**可复用**，不是为持久化铺路 —— 项目明确不做持久化。

仓库同时保管「还没创建的页面」的正文（**草稿**）：

- `saveDraft(title, content)`：写入草稿；
- `draftOf(title)`：只读（弹窗回显用）；
- `takeDraft(title)`：读即消费（取出即移除，创建页面时用）。

草稿的持有者只有仓库一个，所以它**能被看见**：关掉弹窗再打开，
之前写的内容还在，不会被下一次输入悄悄覆盖掉。

### 页面弹窗

点击链接里的页面名，弹出页面弹窗（`PagePopup.vue`）：

- 弹窗里的正文就是一个编辑器，可以直接写（打开时光标已经在里面）
- 页面还不存在时，弹窗顶部提示「这个页面还不存在」并给一个创建按钮
  （这时写的内容先存在仓库的草稿里，点了「创建页面」再写进页面，不会白写；
  关掉弹窗再打开，草稿会**回显**出来，不会被下一次输入覆盖）
- 弹窗里的编辑器是「外部拥有内容」的：父组件在**真正替换内容**（切换页面）时
  递增版本号，编辑器靠版本号判断这次变更是不是自己发起的，
  而不是靠字符串相等——字符串比较一旦被中间层的一次规范化打破，
  就会误判成「内容变了」，把撤销历史清零、光标弹到文末
- 页面里的链接可以继续点开，弹窗用栈记录历史，顶部有「返回」
- 关闭弹窗后焦点回到正文，光标还在原来的位置
- `Esc` 先关候选窗口，再按一次才关弹窗（候选窗口会 `stopPropagation`，不让 `Esc` 冒到弹窗那里）

## 其它交互

- `Cmd/Ctrl + B` 给选区加粗（同时拦截浏览器默认插入 `<b>` 的行为）
- `Cmd/Ctrl + A` 自己实现全选：内容只剩一个空行内元素时（例如源码只剩 `****`），
  浏览器的全选只会得到一个空选区，「全选 + 删除」就删不掉东西
- `Cmd/Ctrl + Z` / `Cmd/Ctrl + Shift + Z` 撤销、重做，历史栈在 `editor/history.ts`
  （换文档时历史重新开始，否则撤销会把上一个页面的内容恢复出来；
  栈最多留 200 条，再多就把最老的丢掉——内存是「条数 × 文档长度」）
- `Cmd/Ctrl + Enter` 打开光标所在的页面链接（只用键盘也能翻页面）
- 粘贴只取纯文本，粘贴进来的内容同样走 Markdown 渲染
- 光标超出视口时自动滚动（输入、退格、撤销都会跟随光标）

## 测试

```bash
pnpm test          # node 侧单元测试（解析器、页面仓库、文本边界、历史栈、架构约束）
pnpm test:browser  # 打包浏览器测试脚本
pnpm test:perf     # 性能回归脚本（独立跑，宽松阈值）
pnpm lint          # ESLint
```

浏览器测试（`test/browser.test.ts`）在真实浏览器里跑，覆盖：

- 四种语法从第一个字符到闭合的完整输入序列
- 闭合后继续输入、退格、撤销重做
- 回车、粘贴、选区替换
- 输入法组合输入（含回车之后在末尾组合输入、以及组合输入被取消）
- 光标在嵌套结构（加粗里的代码、标题里）中的定位
- 双向链接：候选窗口的弹出与关闭、查询词过滤、上下键切换、回车创建页面、点击链接
- 「还没创建的页面」的完整流程（用真实的 App 组件跑）：输入 → 关掉 → 重开还能看到 →
  继续输入 → 创建页面，内容完整
- 源码往返的属性测试：随机生成 300 个样本 + 10 个边界样本，
  断言「解析 → 渲染 → 序列化」回到原文（标记不会被悄悄吃掉）
- 可观察性：查询失败与「没有匹配页面」能区分开、性能统计、日志端口

测试页面会加载应用真实的样式表，所以排版上的问题也能测到：比如「回车之后组合输入的
候选文字必须排在一行里，而不是一字一行」。

浏览器测试脚本打包后是一个静态页面，用任意静态服务器托管即可：

```bash
pnpm test:browser
cd test/dist && python3 -m http.server 8765
# 打开 http://127.0.0.1:8765/index.html
```

页面底部会输出每条断言的结果。
